## 0. 一页看懂 W7

### 0.1 核心矛盾

W6 引入 `AuthService` 后留下一个未决问题：**未登录时业务命令应该怎么办？**

| 选项 | 优点 | 缺点 |
|---|---|---|
| 阻断 | 数据安全，强制用户登录 | 体验差，CLI 每个命令前都要 `auth login`，违背"打开就能用"原则 |
| 放行但不隔离 | 完全兼容老数据，老用户无感 | 多人共享 `user_id=1` 数据，等于 AuthService 形同虚设 |
| **放行 + 隔离**（W7 选定） | 体验和数据安全兼得 | 实现略复杂，user_id 默认 1 让老数据全部归入"匿名用户" |

W7 选了第三种：**未登录不阻断，业务命令按 `user_id=1` 隔离**。

### 0.2 W7 改动总览

| 改动点 | 涉及 SQL/逻辑 | 文件 | 验证 |
|---|---|---|---|
| RecommendService user_id 过滤 | 4 处 `WHERE user_id = ?` | `services/recommend_service.py` | 51 + 4 测试通过 |
| ReportService user_id 过滤 | 12 处 `WHERE user_id = ?` | `services/report_service.py` | 30 + 4 测试通过 |
| CLI 启动 banner 软提示 | 未登录打印 banner | `cli.py` | 1 测试通过 |
| 修复 grade CLI 测试 Popen mock | 6 个测试的 `@patch` 目标 | `tests/test_commands/test_grade_deploy_cli.py` | 19/19 |
| 写 15 个 user_id 隔离集成测试 | 端到端：alice 写的记录 bob 看不到 | `tests/test_services/test_w7_user_id_isolation.py` | 15/15 |

## 1. W7.0 → W7.1 决策阶段

### 1.1 用户原话

> 未登录时不阻断，user_id=1 默认通过

### 1.2 我做的探索（W7.0）

派 1 个 Explore agent 调研：

1. **Service user_id 审计**（5/7 已隔离，recommend / report 未隔离）
2. **6 个 grade 预存失败测试**的根因（当时以为是新代码引入的）
3. **CLI banner 污染分析**（W6 banner 是否会让老测试 output 断言失败）
4. **session / user_id 路径**：未登录时 `get_user_id()` 走默认 1 的路径是否安全

### 1.3 W7.1 关键决策

| 决策点 | 选项 | W7 决定 | 理由 |
|---|---|---|---|
| 未登录时是否阻断 | 阻断 / 放行 / 隔离 | **放行 + 隔离** | 用户明确要求"不阻断"；隔离由 W5 已有的 `get_user_id()` 默认 1 兜底 |
| recommend / report user_id | 单独为它们加 / 不加 | **加** | 跟其他 Service 保持一致；不加等于在 W7 留下"读不隔离"的安全洞 |
| banner 提示 | 阻断 / 静默 / 软提示 | **软提示** | 用户该知道自己在用"匿名"模式，但不强制处理 |
| MySQL 模式 + 未登录 | 拒绝 / 自动建匿名账号 / 跟 SQLite 一样 | **留 W8** | 涉及账号自动创建策略 + MySQL `users` 表 schema，不在 W7 范围 |
| grade 6 个预存 fail | 留 / 修 | **修** | W7.5 集成测试用 `tmp_path` 会跑过这些测试，遗留的 6 个 fail 会让 W7.verify 看着红 |
| write Service 未登录警告 | 加 / 不加 | **不加** | 写操作的 user_id 来源是 `get_user_id()`，跟读一致，没有"写串了"的风险 |

### 1.4 决策的工程价值

最大的隐性收益：**`get_user_id()` 这个 5 行函数救了 W7**。

W5 时（没有任何用户系统）已经把"user_id = env > config > 1"封装成一个函数。W7 时只需要在 `_show_current_user` 里多读一下 `session.json`，未登录分支就自然落到默认 1 上。**如果当时在 W5 写死 `user_id = 1`，W7 就会变成"要么改 30 处硬编码，要么留一个安全洞"二选一。**

## 2. W7.2a 真实 bug：recommend 2 处 SQL 漏改

### 2.1 表面

W7.2a 完成时，我跑 `grep "FROM learning_records"` 报 4 处，全部加了 `WHERE user_id = ?`。`pytest tests/test_services/test_recommend_service.py` 51/51 通过。

一切看着都干净。

### 2.2 真相

W7.5 写集成测试 `TestRecommendUserIdIsolation` 时，第一个测试就失败：

```
FAILED tests/test_services/test_w7_user_id_isolation.py::TestRecommendUserIdIsolation::test_get_due_words_only_returns_own
AssertionError: 'bob_due' in {'alice_due', 'bob_due'}
   用户 1 看到了用户 2 的到期词
```

我重跑 grep，加了行号：

```
65: WHERE user_id = ? AND learn_count > 0            ← 改过了
115: WHERE next_review <= ?                          ← 没改！  ← 真问题
207: "SELECT memory_level, next_review, ... FROM learning_records"  ← 没改！ ← 真问题
```

之前 grep 用了 `WHERE` 关键词，但 `predict_mastery` 那处**根本没有 WHERE 子句**，所以 grep 跳过了；`get_due_words` 那处有 `WHERE` 但 grep 是查 `FROM learning_records` 后的几行匹配，我数错了行号范围。

### 2.3 根因

| 层 | 问题 |
|---|---|
| 工具 | `grep` 报告的"全部匹配"实际只覆盖了有 `WHERE` 的查询；无 `WHERE` 的查询被默默跳过 |
| 验证 | 51 个 recommend 既有测试**没有一条**覆盖"多用户场景"，所以单用户测试全过，掩盖了 bug |
| 过程 | 我在 W7.2a 末尾只说"51/51 既有测试通过"就停了，没有用 `wc -l` 或行数对比确认 4 处都改完 |

### 2.4 修复

`recommend_service.py` L113-120 的 `get_due_words`：

```python
# 改前
WHERE next_review <= ?
(today, limit),

# 改后
WHERE user_id = ? AND next_review <= ?
(self._user_id, today, limit),
```

`recommend_service.py` L206-209 的 `predict_mastery`：

```python
# 改前
"SELECT memory_level, next_review, correct_count, wrong_count FROM learning_records"

# 改后
"SELECT memory_level, next_review, correct_count, wrong_count "
"FROM learning_records WHERE user_id = ?",
(self._user_id,),
```

### 2.5 教训

**经验 A：grep 验证要带行号 + 二次确认无 WHERE 的查询**。

后面 W7.2b 的 report_service 我用 `-A 5` 展开上下文再扫一遍，发现 12 处里也有 5 处漏改（`_get_reviewed_words` / `_get_streak` / `_get_adjacent_dates` / `_get_total_stats` / `_get_all_active_dates`），是同样的工具盲区。**如果 W7.2a 当时就用同样的方法复检，W7.5 集成测试可能第一次就过。**

**经验 B：单用户测试覆盖不到"多用户隔离"**。

这是 SQL 改动的通用陷阱：原有测试都跑在 `user_id=1` 单实例下，加 WHERE 过滤后行为不变，测试自然全过。**只有显式写"用户 1 写，用户 2 读，断言不交叉"才能抓到。** W7.5 集成测试的 `_ensure_table` + 双用户 seed 就是为此而生。

### 2.6 当时对 report 的补救

发现 recommend bug 后，我对 report_service 用了更严格的扫描（`grep -A 5 "FROM learning_records"`），结果命中 12 个 SQL 位置里有 5 个漏改（之前以为 12 个都改完了）。修复后再次全量扫描才 0 遗漏。

**这次 W7.2b 的"补漏"完全是 W7.5 集成测试 + 严格 grep 二次扫描逼出来的。** 没有 W7.5，report 的 5 处漏改会跟 recommend 一样潜伏到 W8。

## 3. W7.4 真实 bug：grade CLI mock 目标错

### 3.1 表面

W6 末已经有 6 个 `test_grade_deploy_cli.py` 失败，我以为这是 W6 引入的。W7.4 决定顺手修。

### 3.2 真相

W7.4 重写 `_VALID_ESSAY`（解决 50 字符预校验）后，6 个测试还是失败：

```
FAILED test_grade_essay_llm_failure
AssertionError: '失败' not in '正在批改...批改结果...四维评分...'
```

老测试断言"失败"在 output 里，但跑出来的是"批改结果 / 四维评分"——说明 **LLM 调用是真实跑通了**，不是 mock 出来的失败。

### 3.3 根因

老测试用的是：

```python
@patch("ielts_buddy.services.grading_service.subprocess.run")
def test_grade_essay_llm_failure(self, mock_run, ...):
    mock_run.return_value = ...
```

但 `grading_service._call_grok` 实际用的是：

```python
process = subprocess.Popen(
    [python_cmd, GROK_PATH, "-", "-s", sp, "--json"],
    stdin=subprocess.PIPE,
    ...
)
stdout, stderr = process.communicate(input=prompt, timeout=120)
```

**`subprocess.run` 跟 `subprocess.Popen` 是两个完全独立的 API，老 mock patch 的是 `run`，运行时根本不会触发 mock**，于是真的 subprocess 跑起来了，grok.py 调 minimaxi.com 返回了正常评分数据，断言失败。

**这个 bug 至少从 W6 之前就存在了**，老测试从来没有真的验证过错误处理路径——它只是"看起来"在做单元测试，实际上每次都在打真 API。

### 3.4 修复

把所有 6 个测试的 mock 目标从 `subprocess.run` 改成 `subprocess.Popen`，并重写 mock helper：

```python
def _make_popen_result(data: dict) -> MagicMock:
    """Popen.communicate 返回 (stdout, stderr) 元组，returncode 在实例上。"""
    content = json.dumps(data, ensure_ascii=False)
    outer = json.dumps({"content": content, "model": "test", "usage": {}})
    mock = MagicMock()
    mock.returncode = 0
    mock.communicate.return_value = (outer, "")
    return mock

# 失败 case
mock_proc = MagicMock()
mock_proc.returncode = 1
mock_proc.communicate.return_value = ("", "API error")
```

### 3.5 教训

**经验 C：mock 目标必须跟代码实际 import 的 API 完全一致**。

`subprocess.run` 和 `subprocess.Popen` 都是 `subprocess` 模块下的 public API，单元测试工具（`unittest.mock.patch`）patch 的是 `import` 的**名字**而不是模块功能。如果代码写 `from subprocess import Popen`，mock 目标就变成 `module.Popen` 而不是 `subprocess.Popen`。

**经验 D：跑通了的 mock 不代表真在拦截**。

老测试从未 fail（至少 W6 之前没 fail）的"成功"路径，断言找到的其实是真 LLM 的回包关键字，跟 mock 一点关系没有。这是 CI 里的"绿灯陷阱"——测试通过，但验证的事完全没发生。

**经验 E：断言关键字要从 mock 数据出，而不是从真生产数据出**。

如果当时 `test_grade_essay_with_text` 的断言是 `"6.5" in output`（mock 数据是 6.5），那 mock 一旦没拦截，断言就会变红暴露问题。**用 mock 数据形状反推断言关键字，是验证 mock 真的生效的最简单办法。**

### 3.6 工程价值

修完这个 bug 之后，6 个 grade 测试在 `tmp_path` 下完全脱离 minimaxi.com，**任何机器上都能跑出相同结果**。这才是单元测试该有的样子。

W7.verify 跑全量时 29 个 fail 全部是 `test_grading_service.py::TestErrorStats`——那些是 `grading_service` 自己内部的测试，**没有走 subprocess mock 路径**，是直接 `svc._call_grok(...)` 调用真 LLM 的，**这是另一类遗留问题**（应该用 `httpx mock` 或在测试里直接 monkeypatch `_call_grok`），不在 W7 范围，留 W8+。

## 4. 工程经验总结

### 4.1 W7 的 5 条工程经验

1. **grep 验证 SQL 改动要带行号 + 二次展开上下文**（经验 A）
2. **单用户测试覆盖不到多用户隔离**（经验 B）
3. **mock 目标要跟代码 import 的 API 名完全一致**（经验 C）
4. **绿灯测试可能是"假绿"**（经验 D）
5. **用 mock 数据形状反推断言**（经验 E）

### 4.2 W7 的 3 个隐性收益

| 收益 | 说明 |
|---|---|
| 报告不再"看错人" | recommend / report 12+4=16 处 SQL 隔离，alice 登录看到的薄弱词和报告全是他自己的，bob 同理 |
| 老测试不再"假绿" | 6 个 grade 测试现在真在验证 mock 路径，CI 才有意义 |
| `get_user_id()` 抽象的复利 | W5 写的 5 行函数，W7 拿来直接用，没有这一层封装 W7 得多改 30 处 |

### 4.3 W7 的 1 个明确债务

**MySQL 模式 + 未登录的处理未决**：

- SQLite 默认 `user_id=1` 行得通，因为 SQLite 的 `learning_records` 不带外键，alice 的"匿名数据"在 W7 之前就在那
- MySQL 模式如果同样走默认 1，会污染 `user_id=1` 的"系统种子用户"（W3 设计的 system seed）
- 决策选项：自动建 anonymous 账号 / MySQL 模式下要求必须登录 / MySQL 模式默认拒绝

W8 决策点。
