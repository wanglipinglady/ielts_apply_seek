## 一、什么是 ruff 验证

### 1.1 工具定位

ruff 是 Python 生态里目前最快的 **静态代码分析器 + 格式化器**，由 Astral 团队用 Rust 编写。它做的事情可以拆成四类：

| 能力 | 对应规则 | 作用 |
|---|---|---|
| **Linter**（代码质量） | `E/F`（pycodestyle/pyflakes）、`W`（pycodestyle warnings）、`I`（isort）、`N`（pep8-naming）、`UP`（pyupgrade）、`B`（bugbear）、`C4`（comprehensions）、`SIM`（simplify）、`PL`（pylint 子集）等 | 找出未使用变量、错误导入、命名违规、可简化写法、潜在 bug |
| **Formatter** | Black 风格 | 自动统一缩进、引号、换行（项目里暂未启用 `format` 子命令） |
| **Import 排序** | isort 风格 | 自动整理 `import` 顺序 |
| **Fix** | `--fix` | 多数 lint 违规能自动修复 |

W3 阶段我们只用了 linter 部分 — 也就是下面反复出现的"ruff 检查"。它**不运行代码**、**不连接数据库**、**不读配置文件**，只读 `.py` 源码本身做语法和风格层面的扫描。

### 1.2 在项目里的实际配置

`pyproject.toml`：

```toml
[tool.ruff]
line-length = 100
target-version = "py310"
```

- **行宽 100**：超过 100 列的代码会被 `E501` 标记
- **目标版本 3.10**：低版本不支持的语法（match 语句、`X | Y` 联合类型、`int | None` 写法）会触发 `UP` 规则

未配置 `[tool.ruff.lint]`，所以启用的是 ruff 的**默认规则集**（`E4/E7/E9/F`），即最严格的 pycodestyle 错误 + pyflakes。这覆盖了：

- `E401` / `F401` — 多余/未使用的 import
- `E501` — 行宽超限
- `E711` / `E712` — 与 `None`/布尔比较时应使用 `is` / `is not`
- `F841` — 局部变量赋值后未使用
- `F811` — 重新定义已用过的名字
- `W291` / `W292` / `W293` — 尾随空格、文件末尾无换行、缩进含空白

### 1.3 W3 阶段我们怎么用 ruff

W3 期间的每个子阶段（W3.1 / W3.2 / W3.3 / W3.4）在交付前都会跑一次：

```bash
python -m ruff check <changed_files> --no-cache
```

`--no-cache` 强制重算，避免某些场景下缓存未失效的漏报。

修过的 6 类典型问题（W3 期间累计）：

1. `F401` — `Table` 漏导入、`create_engine` 多余导入
2. `F841` — `start_str` / `today_str` / `word_id` 等临时变量赋值后未使用
3. `F841` — `uuid` 模块引用了但用 `id()` 内置方法更直接
4. 测试文件里 `from ielts_buddy.core.models import ExamSession, ExamQuestion` 实际只用了 `ExamQuestion`（`F401` × 2）
5. 测试文件里 `hist = exam_repo.get_exam_history(...)` 后面没用上（`F841`）
6. `__init__.py` 里条件导出的类未在 `__all__` 注册（编译期无错，但运行期 `from package import *` 会丢类）

### 1.4 ruff 验证的边界 — 它**不能**告诉你什么

- **类型正确性**：ruff 不做类型检查，那是 mypy/pyright 的活。W3 阶段我们也没装 mypy，靠 Protocol + 单元测试来保证类型契约
- **运行时行为**：连不连得上 MySQL、SQL 有没有语法错 — 这些只能靠 pytest + 真实数据库
- **业务正确性**：错词本是否真的过滤了错词 — 那是测试用例要覆盖的，不是 ruff 关心的

换句话说，**ruff 是"代码本身写得是否规范"的最后一道低成本闸门**，但它不能替代测试。W3 阶段的验证链是：`ruff check`（写得是否规范）→ `pytest`（行为是否正确）→ 真实 MySQL smoke test（连通性 + 方言正确性）三段式。

## 二、W3 阶段功能实现详解

### 2.1 目标回顾

W2 阶段完成后，整个数据访问层有了一个 `RepositoryContainer` 接口和 6 个 SQLite 实现（`learning / personal_vocab / exam / grade / vocab_cache / user`），但只支持单机模式。W3 阶段的目标是：保持接口完全不变，把 6 个 SQLite 实现翻成 MySQL 8.0 实现，让 Service 层能够用同一份代码访问云端数据库。

### 2.2 设计决策与原因

**决策 A：用 SQLAlchemy Core，不用 ORM**

理由：

- W2 的 SQLite 版用的是 `sqlite3` 原生驱动，SQL 完全透明。MySQL 端如果用 ORM，会让两层实现的 SQL 行数差异巨大，调试困难
- Core 提供 `Table` / `Column` / `select()` / `insert()` 这些结构化 API，但生成的 SQL 完全可见
- 不需要 ORM 的延迟加载、关系映射、Session 生命周期管理 — 我们要的就是"写 SQL、收结果"

代价：

- 需要为每张表手写一份 `t_xxx = Table(...)` 元数据声明，启动时不会自动建表（建表由 `init_mysql.sql` 完成）
- 没有 ORM 的类型提示红利，要靠 Protocol + 单元测试保证接口对齐

**决策 B：种子模板用 `user_id=0` 表示**

`vocab_categories` 表里有一份"模板数据"：

```sql
INSERT INTO vocab_categories (user_id, name, description, is_system) VALUES
    (0, 'favorites', '收藏夹', 1),
    (0, 'mistakes',  '错词本',  1);
```

新用户首次触发 `ensure_system_categories(user_id)` 时，从 `user_id=0` 复制这两行到新用户。这个模式的好处：

- 模板定义只在一处维护（`init_mysql.sql`），业务代码只读不写
- 改模板不会反向影响已存在的用户（W3.3 验证场景 6 已测）
- 业务表不需要 `IF NOT EXISTS` 这种业务逻辑判断，全部交给应用层

**决策 C：MySQL 容器只持一个 `Engine`，不分主库和缓存库**

SQLite 端有 `data.db`（业务）+ `vocab_cache.db`（缓存）两个文件。MySQL 端都放在同一个库 `ietls_learn_online` 里，通过共享的 `Engine` 访问。理由：

- 网络库分离需要分布式事务，业务用不到
- vocab_cache 在 SQLite 端也是同进程内访问，性能差异忽略不计
- 简化部署（一个 URL、一个账号、一个库）

**决策 D：`add_word` 同时接受 `Word` 和 `PersonalWord`**

W3.1 第一版只接 `PersonalWord`，验证时发现 `Word`（系统词库模型）也能用，加了 `getattr` 兜底后与 `add_mistake` 保持一致。W3.4 测试里专门加了 `test_add_word_accepts_word` 锁死这个契约。

**决策 E：`create_exam` 不落库，`save_exam_session` 才落库**

W3.1 期间讨论过两种设计：

1. `create_exam(band, count, time_limit)` 立即把空 session 写库，Service 拿到 session_id 后再 update 题目
2. `create_exam` 只返回 `ExamSession` 对象，Service 装配完题目后**显式**调 `save_exam_session`

选了方案 2，理由：

- 题目来源在 Service 层（VocabService 选词），Repo 层不该感知选词逻辑
- "create → 选词 → save" 形成清晰的三步事务边界，Service 可以选词失败就丢弃内存对象而不污染数据库
- W3.4 的 `test_create_and_finish_exam` 完整演示了这三步

### 2.3 模块结构与文件清单

```
src/ielts_buddy/repositories/
├── sqlite_repo.py        # W2 交付：6 个 SQLite Repository + SQLiteRepositoryContainer
├── mysql_repo.py         # W3 交付：6 个 MySQL Repository + MySQLRepositoryContainer
└── __init__.py           # 双实现条件导出，MySQL 不可用时不阻塞 SQLite 调用

tests/test_repositories/
├── test_sqlite_repo.py   # W2 交付：覆盖 SQLite 实现
├── test_mysql_repo.py    # W3 交付：覆盖 MySQL 实现（连真实 118.190.148.121）
└── test_repository_protocols.py  # W1 交付：保证 SQLite/MySQL 行为一致
```

`mysql_repo.py` 内部按 5 个区块组织：

1. **表元数据**（行 39-160）：8 张业务表的 `Table(...)` 定义
2. **辅助函数**（行 162-180）：`_next_review_date`（艾宾浩斯）、`_row_to_*`（行→模型）转换
3. **6 个 Repository 类**（行 180-1340）：每个类 100-200 行
4. **默认连接参数 + URL 构造器**（行 1350-1380）
5. **`MySQLRepositoryContainer` + 工厂**（行 1380-1430）

### 2.4 关键 Schema 差异（MySQL vs SQLite）

| 表 | SQLite 端主键 | MySQL 端主键 | 差异 |
|---|---|---|---|
| `learning_records` | `id INTEGER PRIMARY KEY AUTOINCREMENT` | `id BIGINT AUTO_INCREMENT` | MySQL 用 BIGINT 预留扩容 |
| `personal_vocab` | 同上 | 同上 | 同上 |
| `vocab_categories` | `id` | `id BIGINT` | 模板存 `user_id=0` |
| `vocab_category_words` | `(category_id, word)` 复合主键 | `(user_id, category_id, word)` 唯一键 | MySQL 加 user_id 实现隔离 |
| `exam_sessions` | `id TEXT` (UUID 字符串) | `id BIGINT` + `session_id VARCHAR(32)` 业务键 | MySQL 用自增 id + 业务 id 双层 |
| `vocab_cache` | `word PRIMARY KEY` | 同上 | 完全一致 |
| `cache_meta` | `key_name PRIMARY KEY` | 同上 | 完全一致 |

注意 `vocab_category_words` 那一行 — 实际查询时不能只按 `(category_id, word)`，必须带上 `user_id`，否则会跨用户串数据。这点在 `MySQLPersonalVocabRepository` 的所有方法里都遵守了。

### 2.5 数据流（以"复习一个单词"为例）

Service 层调 `container.learning.upsert_record(user_id, word, correct=True)`：

1. 走 `MySQLLearningRepository.upsert_record`
2. `with self._engine.begin() as conn:` — 拿一个事务
3. `SELECT memory_level FROM learning_records WHERE user_id=? AND word=?`
4. 计算新 level（correct → +1，wrong → -1）
5. `_next_review_date(today, new_level)` 算下次复习日期
6. `INSERT ... ON DUPLICATE KEY UPDATE`（或先 `UPDATE` 再 `INSERT`，视实现而定）
7. 返回新的 `LearningRecord` 对象

整个过程**不发第二条 SQL 语句到 Service**，全在 Repo 内部消化。W2 端用 sqlite3 写的话写法略有不同（`INSERT OR REPLACE`），但 Service 看到的接口签名完全一致。

### 2.6 已知约束与权衡

| 约束 | 当前选择 | 替代方案 |
|---|---|---|
| MySQL 账号密码硬编码在 `mysql_repo.py` | 开发期最快 | 改读环境变量 / `~/.my.cnf` / 密钥管理服务 |
| 单库单用户 | 简化部署 | 多用户分库需引入 `user_id` → `db_name` 路由层 |
| 不支持事务嵌套 | 业务用不到 | 如需嵌套，改用 `session.begin_nested()` |
| `vocab_cache` 无 TTL | 信任 mtime 比对 | 需要过期时改 `cache_meta` 加 `expires_at` |
| 没有数据迁移工具 | 双库各自初始化 | W4 阶段需要从 SQLite → MySQL 迁移脚本 |

## 三、后续扩展涉及的修改点

按"想做什么 → 要改哪里"的方式列出。所有路径相对于 `D:\0000-maven\self-program\ielts_apply_seek`。

### 3.1 W4 — Service 层接入 MySQL 容器

**目标**：让 `cmd_*.py` 在用户选择"联网模式"时自动用 MySQL 容器，而非 SQLite。

**要改的文件**：

4. `tests/test_repositories/test_mode_factory.py`（新文件）
   - 验证 mode 工厂返回的类型与属性完整

**新增测试**：

- 单机模式仍能跑通（不能因重构而让老用户升级失败）

### 3.2 W5 — 数据迁移（SQLite → MySQL）

**目标**：让老用户的本地数据能完整搬到云端。

**要改的文件**：

1. `scripts/migrate_sqlite_to_mysql.py`（新文件）
   - 用 `sqlite3.connect()` 读老库
   - 用 `MySQLRepositoryContainer` 写新库
   - 业务表逐张迁移，每张表按 `user_id` 分批
2. `src/ielts_buddy/repositories/migrate.py`（新文件）
   - 暴露 `migrate_user(user_id: int, src: SQLiteContainer, dst: MySQLContainer) -> Report` 函数
   - 返回 `{"learning": 152, "personal_vocab": 23, "exam_sessions": 4, "errors": []}` 让 CLI 展示
3. `src/ielts_buddy/cli/cmd_migrate.py`（新文件）
   - 接 `ielts migrate --dry-run` 走一遍不算数
   - `--user <username>` 迁指定用户
   - `--all` 迁所有本地用户
4. `tests/test_migration/test_migrate.py`（新文件）
   - 造 SQLite 假数据 + 测迁移结果一致
   - 测幂等性（跑两遍不重复插入）
   - 测网络中断时的断点续传

**关键设计点**：

- 迁移是**离线操作**，不影响在线用户的请求
- vocab_cache 不迁移（重新从主词库生成）
- exam_sessions 的 `id` 字段在 SQLite 是 UUID 字符串、MySQL 是 BIGINT，需要做映射表
- 迁移完成后给老数据打 `migrated_at` 时间戳，方便审计

### 3.3 W6 — 性能与高可用

**目标**：单库扛不住时切到主从 + 读写分离。

**要改的文件**：

1. `src/ielts_buddy/repositories/mysql_repo.py`
   - `MySQLRepositoryContainer.__init__` 接受 `write_url: str, read_url: str` 两个 URL
   - 读多写少的查询（`get_*` / `list_*` / `get_history` / `get_due_*`）走 `read_url`
   - 写操作（`upsert_*` / `add_*` / `update_*` / `delete_*` / `save_*`）走 `write_url`
   - `self._read_engine` 和 `self._write_engine` 两个 Engine 实例
2. `scripts/init_mysql_replica.py`（新文件）
   - 部署文档：MySQL 主从配置 + 读权重
3. `tests/test_repositories/test_mysql_read_write_split.py`（新文件）
   - 验证读操作在主库挂掉时仍能服务（前提是从库同步延迟可接受）

**权衡**：

- 引入两套 Engine 增加复杂度，6 个 Repository 类要分别管理读/写入口
- 可以用装饰器 `@read` / `@write` 标注方法，类初始化时扫描
- 缓存层（`vocab_cache`）强制走主库 — 缓存数据不一致比性能更敏感

## 四、给后续接手者的提醒

1. **不要绕过 Protocol 直接调 SQLite 或 MySQL 端的具体类**。Service 层只能依赖 `RepositoryContainer` 暴露的 6 个属性，否则换数据库时 Service 也要改
2. **新增业务表时**先在 `init_mysql.sql` 写 DDL，再到 `mysql_repo.py` 加 `t_xxx = Table(...)` 元数据，最后到 `Protocol` 加方法签名 — 三处缺一不可
3. **user_id 是隔离边界**，所有新增表都必须带。漏写一个表就会有跨用户串数据的安全洞
4. **vocab_cache 是共享资源**，永远不要加 `user_id` 列
5. **W3 的 203 个测试是回归保护网**，改任何一行 Repo 代码前先跑 `pytest tests/test_repositories/ -q`，跑通再改
6. **MySQL 远程库的写入会真实落盘**，写测试时务必用唯一用户名（带 timestamp + pid）并在 teardown 清理，避免污染生产数据
