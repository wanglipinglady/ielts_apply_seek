## 2. 经验提炼

在 12 个具体问题之上，有 4 条更普适的工程守则，是 W1/W2 反复出现的：

**守则 1：抽象层加新方法前，先查"旧代码会怎么调它"**。W2.2 改造 Service 时，`ReviewService` 加了 `_conn`/`_db_path` 两个 `@property` 才让旧测试零修改通过；`GradingService` 没暴露 `_conn` 也只跑 7 个测试。这条原则的价值是"改造完成后能立刻跑通既有 374 个测试"。

**守则 2：跨进程/跨工具的接口，要用幂等 + 显式 close**。SQLite 的 `database is locked` 错误、Windows 文件句柄延迟释放、pytest fixture 的 teardown 顺序，都是这一类。规律是"打开资源时谁负责打开，关闭时谁负责关闭，避免依赖 GC"。

**守则 3：避免模块循环依赖的最稳办法是"接口不调实现"**。W2 的 `PersonalVocabService.import_words` 内部逻辑一旦放回 Repository 就会循环。改成"Repository 自己实现 import/export 纯 SQL 版本，Service 委托过来"——打破循环的同时不损失可测试性。

**守则 4：测试 Protocol 风格的接口时，运行时的 `inspect.signature` / `__annotations__` 与 `dir()` 行为不同**。这是 PEP 544 的一个易错点；遇到"Protocol 属性读不到"先去 `__annotations__` 找，不要在 `dir()` 上反复尝试。

## 3. W1 阶段问题

W1 的核心交付是 `src/ielts_buddy/core/repository.py`（6 个 Protocol + 容器 + assert 工具）和 `core/models.py` 的 9 个 `user_id` 字段新增。

### P1 · `python` 命令在 PowerShell 不可用

**现象**：`python -c "import sys; print(sys.version)"` 报命令找不到，但 `py` 或 `python3` 在某些上下文能调起来。

**排查**：用 `where.exe python` 查 PATH，发现 `D:\Program Files (x86)\Python3.13.3\python.exe` 在 PATH 里，但 PowerShell 解析时命中了 TRAE 的 shim，shim 把 `python` 重定向到另一个不存在的解释器。

**根因**：Windows 系统的 `PATHEXT`/PATH 优先级与 PowerShell profile 注入的 shim 冲突。TRAE 在用户级别注册了一个名为 `python.exe` 的 shim，它抢先于真实解释器响应。

**解决**：所有命令统一用绝对路径：

```powershell
& 'D:\Program Files (x86)\Python3.13.3\python.exe' -m pytest tests/
```

**原理**：PowerShell 的命令解析遵循"先 alias → 再 function → 再 cmdlet → 再 application"；shim 在 application 阶段被命中。绝对路径绕过整个解析过程。

**涉及技术点**：
- Windows PowerShell 命令解析优先级
- PATH 顺序与 `PATHEXT` 关联
- shim（垫片）模式的应用场景

### P2 · `pip install` 退出码 1 但看不到错误

**现象**：`pip install pytest ruff` 报 exit 1 但终端只显示 `Exit code: 1`，没有 traceback。

**排查**：用 `python -m pip install pytest 2>&1 | Tee-Object -FilePath install.log` 把输出落盘，发现错误是 `Access is denied` 写到 `%LOCALAPPDATA%\pip\cache`。

**根因**：PowerShell 的 `2>&1 | Select-Object -Last 20` 这种管道 + 后置选择器，会在子进程退出后丢弃未被选中的行——而 pip 的错误输出是写到 stderr 的，混入 Select-Object 的过滤时被吞掉。

**解决**：分两步执行，先安装再用 `pip show` 验证：

```powershell
& 'D:\Program Files (x86)\Python3.13.3\python.exe' -m pip install pytest
& 'D:\Program Files (x86)\Python3.13.3\python.exe' -m pip show pytest
```

**原理**：PowerShell 管道是流式消费，被 `Select-Object -Last N` 截断时，前面的对象已经出管道不会回到屏幕。要保留完整输出需要 `Out-File` 或 `Tee-Object`。

**涉及技术点**：
- PowerShell 管道流式消费模型
- `2>&1` 重定向只在单条命令中有效
- pip 的缓存目录与权限模型

### P3 · ruff `.ruff_cache` 权限错误

**现象**：执行 `ruff check src/` 报 `PermissionError: [Errno 13] Access denied: '.ruff_cache'`。

**排查**：查 `dir .ruff_cache` 显示所有者是另一个用户（`Administrator`），当前用户没有写权限。

**根因**：多个项目共享一个工作区根目录下的 `.ruff_cache`，缓存目录被先执行的进程创建，后续进程尝试以不同用户身份写就失败。

**解决**：在所有 ruff 命令上加 `--no-cache`：

```powershell
& 'D:\Program Files (x86)\Python3.13.3\python.exe' -m ruff check src/ --no-cache
```

或者为每个项目设置 `RUFF_CACHE_DIR` 环境变量指向项目内独立目录。

**原理**：ruff 跟 mypy/eslint 类似，会在工作区根目录创建 cache 加速二次检查。Windows 的 ACL 比 Linux 更严格，跨用户的目录写会立刻失败。

**涉及技术点**：
- 工具缓存的归属与权限
- 跨用户协作时的环境隔离
- ruff 的 cache key 机制

### P4 · ruff 报未使用的 import

**现象**：`ruff check src/ielts_buddy/core/repository.py` 报 `F401 date, datetime imported but unused`。

**排查**：阅读 repository.py 文件，发现 `from datetime import date, datetime` 写在顶部但全文没用到。

**根因**：写 Protocol 时按"未来可能要用"的思路 import 了 date 和 datetime，但本批次没用到。

**解决**：删除该行。ruff 的 F401 是 linter 经典规则——import 但未使用是"死代码"的信号。

**原理**：Python 社区对"未使用 import"的态度比较严格（Go 反而容忍），原因是 IDE 折叠后会成为噪声。linter 把这种"未来可能用"挡住，强制开发者按需 import。

**涉及技术点**：
- Python 命名空间与 import 系统
- ruff 的规则集（F401, E501, ...）
- 静态分析工具的覆盖范围

### P5 · 测试 Pydantic 模型时 `m()` 默认构造失败

**现象**：写 `LearningRecord()` 想拿一个空实例做断言，结果报 `ValidationError: word_id Field required`。

**排查**：看 `core/models.py` 的 `LearningRecord` 定义，`word_id: int` 没有默认值。

**根因**：业务模型把 `word_id` 设为必填（因为学习记录必须关联单词），但测试想用最小数据做类型断言。

**解决**：为每个被测试的模型准备最小数据 dict：

```python
LearningRecord(word_id=1)
TestSession(session_id="x", test_date="2026-07-01T00:00:00",
            test_mode="spelling", total_count=1, correct_count=1)
```

**原理**：Pydantic v2 默认所有非 `Optional` 字段都是必填。可以用 `model_construct()` 绕过校验，但只在测试场景用——生产代码应让 Pydantic 校验失败暴露 bug。

**涉及技术点**：
- Pydantic v2 的 `BaseModel` 必填语义
- `model_construct` vs `__init__` 的区别
- 测试中"如何生成合法 fixture"的模式

### P6 · Protocol 方法签名 `params[0]` 取错

**现象**：`test_repository_protocols.py` 首跑 38 个 fail，错误是 `AssertionError: expected 'user_id' as first param, got 'self'`。

**排查**：在测试里 `inspect.signature(ProtocolClass.method)` 拿参数列表，取 `params[0]` 当作"第一个业务参数"，结果拿到的是 `self`。

**根因**：`typing.Protocol` 的方法定义 `def method(self, user_id: int, ...)` 在 `inspect.signature` 中返回的参数列表**包含 `self`**（虽然 Protocol 的方法本身不绑定实例，但签名读取按 Python 普通方法处理）。

**解决**：测试断言改为取 `params[1]`（跳过 `self`）：

```python
params = list(inspect.signature(ProtocolClass.method).parameters)
assert params[1].name == "user_id"
```

**原理**：`Protocol` 类的 `__annotations__` 不带 `self`，但 `inspect.signature` 在拿到方法后默认按"绑定方法"理解。判断 `self` 的标准办法是看 `parameter.kind == Parameter.POSITIONAL_OR_KEYWORD`，更稳。

**涉及技术点**：
- `typing.Protocol` 与抽象基类（ABC）的区别
- `inspect.signature` 的参数解析规则
- `Parameter.kind` 的枚举值

### P7 · `RepositoryContainer` 的属性 `dir()` 看不到

**现象**：测试 `TestProtocolConsistency::test_required_attrs_exist` 报 `AttributeError: 'RepositoryContainer' has no attribute 'learning'`。

**排查**：手敲 `from ielts_buddy.core.repository import RepositoryContainer; RepositoryContainer.learning` 同样报错。但 `RepositoryContainer.__annotations__` 里有 `learning: LearningRepository`。

**根因**：`Protocol` 类只声明"实例应有什么属性"，不实现这些属性。`dir()` 只能列出已定义的成员，**不会列出 Protocol 的 `__annotations__` 字段**——这是 PEP 544 设计的核心：Protocol 是类型契约，不是运行时类。

**解决**：测试改用 `__annotations__` 读：

```python
assert "learning" in RepositoryContainer.__annotations__
assert "personal_vocab" in RepositoryContainer.__annotations__
```

**原理**：PEP 544 让 Protocol 在运行时是"鸭子类型"——只要一个类实现了 `__init__` 里声明的属性，就被认为是 Protocol 的实现。验证这一点的标准库函数是 `typing.runtime_checkable` + `isinstance(obj, ProtocolCls)`，但仅当 Protocol 有 `__call__` 类的方法才能用，**纯属性协议不能 isinstance 检查**。

**涉及技术点**：
- PEP 544 协议机制
- `runtime_checkable` 协议的边界
- 静态 duck typing 的验证模式

### P8 · 旧表缺 `user_id` 列导致测试失败

**现象**：跑 `test_review_service.py` 报 `sqlite3.OperationalError: no such column: user_id`，而且 `IF NOT EXISTS` 没生效——因为表已经存在但没这列。

**排查**：用 DB Browser 看 `~/.ielts-buddy/data.db`，发现 `learning_records` 表是旧 schema（`word TEXT UNIQUE`，没有 `user_id/source` 列）。新 `_SCHEMA` 里的 `CREATE TABLE IF NOT EXISTS` 看到表已存在就跳过，**但 `CREATE INDEX IF NOT EXISTS idx_lr_user_review ON learning_records(user_id, ...)` 仍会执行**，引用不存在的列。

**根因**：SQLite 的 `CREATE TABLE IF NOT EXISTS` 是"存在则不建"，不会做 schema 比对。DDL 里夹带的 `CREATE INDEX` 没做列存在性检查。

**解决**：写 `_migrate_legacy_schema()` 在 `_SCHEMA.executescript()` 之前先补列：

```python
def _migrate_legacy_schema(conn):
    for table, columns in _MIGRATIONS.items():
        row = conn.execute(
            "SELECT name FROM sqlite_master WHERE type='table' AND name=?",
            (table,),
        ).fetchone()
        if row is None:
            continue
        existing = {r[1] for r in conn.execute(f"PRAGMA table_info({table})").fetchall()}
        for col_name, col_def in columns:
            if col_name not in existing:
                conn.execute(f"ALTER TABLE {table} ADD COLUMN {col_name} {col_def}")
    conn.commit()
```

**原理**：`PRAGMA table_info(table)` 返回列定义的元数据，是 SQLite 的"反射"接口。`ALTER TABLE ADD COLUMN` 是 SQLite 唯一支持的模式变更操作（不能改类型、不能删列），但补列足够覆盖"v1 → v2 加字段"的迁移场景。

**涉及技术点**：
- SQLite 的 DDL 限制（不能 DROP COLUMN，但能 ADD COLUMN）
- 模式迁移的反模式：直接重建表（会丢数据）
- `sqlite_master` 系统表与 `PRAGMA` 系列函数

### W1 · `Service.import_words` ↔ `Repository.import_words` 死循环

**现象**：跑 `test_personal_vocab_service.py` 时测试**挂起 6 分钟不返回**，CPU 占用正常但栈很深。

**排查**：在 `import_words` 入口加 `print()` 看到日志在无限重复。

**根因**：
1. `SQLitePersonalVocabRepository.import_words(user_id, file_path, ...)` 调用 `self.add_word(user_id, pw)`，正常
2. `SQLitePersonalVocabRepository.add_word(user_id, pw)` 会触发 `_ensure_system_categories(user_id)`，对 `vocab_categories` 表做 `INSERT OR IGNORE`，正常
3. **问题路径**：Repository 初始实现是"调 Service 委派"，即 `import_words` → 新建 `PersonalVocabService()` → 调 `svc.import_words()` → `svc.add_word()` → 走 Repository 的 `add_word` → 又触发……

```
Service.import_words
  → Repository.import_words (临时构造 Service)
    → Service.import_words
      → Service.add_word
        → Repository.add_word
          → Repository._ensure_system_categories
            → INSERT OR IGNORE
```

循环的实际位置是"每次进入 `Repository.import_words` 都新建一个 Service"。虽然单次循环很短，但导入 N 个单词时栈深 O(N)，最终**栈溢出或测试卡死**。

**解决**：放弃 Service 委派，把 import/export 的 100+ 行逻辑用纯 SQL 直接写到 Repository 里。关键点：
- `add_word` 走 Repository 自带的实现，不回调 Service
- JSON 解析、CSV 解析、循环写入都内联在 `import_words` 里
- 一次循环，栈深 O(1)

**原理**：模块间循环依赖在编译期不会立刻报错（import 在函数体内），但在运行时第一次调用时栈展开。`time.sleep` / 调试器断点也看不出，因为没有真正"死循环"，是"短循环 * 大量迭代"。

**涉及技术点**：
- Python 的 import 时机（模块级 vs 函数体级）
- 栈深与"伪死循环"的调试模式
- Repository 模式与 Service 模式的职责划分（"委派"vs"内联"）

### W2 · PowerShell `&&` 不支持

**现象**：`cd 'D:\0000-maven\self-program\ielts_apply_seek' && python -m pytest` 报 `The token '&&' is not supported. & was unexpected.`

**排查**：bash 习惯用 `&&` 串联命令，PowerShell 5 不支持。

**根因**：PowerShell 5 的语法是分号 `;` 串联，`&&` 是 PowerShell 7 才加入的。Windows 默认装的是 PowerShell 5（Windows PowerShell）。

**解决**：用 `;` 替代 `&&`，或把命令拆成两个独立 RunCommand 调用。

**原理**：PowerShell 5 的 `&` 是"调用操作符"（call operator），如 `& 'python.exe' -m pytest`。`&&` 在 PowerShell 7 才被引入为"前一个命令成功才执行下一个"。

**涉及技术点**：
- PowerShell 5 vs PowerShell 7 语法差异
- `& ` / `;` / `|` / `2>&1` 操作符语义

### W3 · SQLite Windows 文件锁

**现象**：`tests/test_repositories/test_sqlite_repo.py` 首跑 60 个测试，**59 个 fail**，错误是 `sqlite3.OperationalError: database is locked`。

**排查**：第一个测试跑完清理 tmpdir 时删 `data.db`，但 SQLite 进程还持有 Windows 文件句柄；下一个测试又新建同名文件，触发 "Access is denied" 或 "database is locked"。

**根因**：Windows 的文件锁模型与 Unix 不同——`os.unlink()` 不会等文件句柄释放，而是标记"待删除"，但**新打开同名文件会失败**。SQLite 在 Windows 上是文件级锁，conn 关闭后 GC 可能延迟几秒。

**解决**：

1. fixture `yield` 之后显式 `c.close()`：

```python
@pytest.fixture
def container(tmp_dir):
    c = SQLiteRepositoryContainer(db_path=tmp_dir / "data.db", cache_path=tmp_dir / "vocab_cache.db")
    yield c
    try:
        c.close()  # 显式关闭 conn
    except Exception:
        pass
```

2. Windows 上 `tmp_dir` 每次测试是 `tempfile.TemporaryDirectory()`，目录名是唯一的（`tmpdirxxx`），但**目录里的 `data.db` 文件名是固定的**。这意味着下一个测试可能复用同名文件。所以更稳的方案是给每个测试 unique 文件名。

**原理**：SQLite 的 Windows 后端走 `LockFileEx`/`UnlockFileEx` Win32 API，文件句柄的释放顺序是 "→ FILE_FLAG_DELETE_ON_CLOSE → 实际删除"。如果连接在 try/finally 里没显式 close，Python 的 GC 触发时机不可控。

**涉及技术点**：
- Windows 文件系统与 Unix 的差异
- SQLite 三种 journal 模式（DELETE / WAL / MEMORY）对并发的影响
- pytest fixture 的 setup/teardown 时机
- `tempfile.TemporaryDirectory()` 的实现

### W4 · `@property _conn` 无法被 monkey-patch

**现象**：Repository 的 `import_words` 写了一段 `svc._conn = self._conn`，但运行时 `svc._conn` 还是 None。

**排查**：看 `Service` 类，`_conn` 是 `@property` 装饰器实现的**只读**属性，没有 setter。

**根因**：`@property` 默认只暴露 getter，外部赋值会抛 `AttributeError: can't set attribute`。原来"委派 Service"的方案依赖能改 `svc._conn` 指向新的 conn——这个用法在 property 模式下不可行。

**解决**：彻底放弃"在 Repository 里调 Service 实例"的做法，把 import/export 逻辑直接写到 Repository 里走纯 SQL（见 W1 的最终方案）。

**原理**：`@property` 的本质是把方法伪装成属性，它不创建实例属性，赋值时 Python 不会去改方法而是查 setter，没有 setter 就抛错。类比 Java 的 `final` 字段、Go 的非导出字段。

**涉及技术点**：
- Python descriptor 协议
- `@property` 的 getter / setter / deleter
- 不可变对象的设计模式

## 5. W2 的 5 个 sqlite_repo.py 关键设计

## 8. 给 W3+ 工作的预警

W3 阶段会写 `MySQLRepository`、接入 SQLAlchemy/PyMySQL、连接真实 MySQL（`118.190.148.121:3306`）。基于 W1/W2 的经验，预计会踩到这些坑：

**预警 1：MySQL 与 SQLite 的方言差异**。MySQL 用 `BIGINT PRIMARY KEY AUTO_INCREMENT`、字符集 `utf8mb4`、引擎 `InnoDB`；SQLite 用 `INTEGER PRIMARY KEY AUTOINCREMENT`、无引擎概念。建议在 `repositories/mysql_repo.py` 里把方言差异**显式抽成 helper**，不要散落在每个方法里。

**预警 2：连接池 vs 单连接**。SQLite 适合单连接；MySQL 必须用 SQLAlchemy 的 `create_engine` + `sessionmaker`，否则高并发下会触发 "Too many connections"。W3 阶段需要决定是"每个 Repository 方法开一个 connection"还是"共享 engine 池"——前者简单，后者性能高。

**预警 3：测试容器的复杂度**。W3 的 `test_mysql_repo.py` 必须能跑通，需要考虑：测试库与生产库隔离、CI 是否启用 testcontainers、网络延迟导致测试慢。建议在 `conftest.py` 提供一个"如果有 MYSQL_URL 环境变量就连真实库，否则 skip"的 fixture。

**预警 4：`init_mysql.sql` 已经在 W1 准备过**（8 张表 + 2 个种子分类），但 W3 启动时要先确认云端 DB 状态——如果用户在 W1 之后手动建过表，init 脚本的 `IF NOT EXISTS` 会跳过但可能 schema 不一致。**建议 W3 启动前跑一次 `init_mysql.py --check-only`** 做对比。

## 9. 附录：复盘方法说明

**为什么做这次复盘**：项目里没有 PM，开发者要自我管理"为什么这样改"的解释链。否则 6 个月后再看 W1/W2 的代码会忘记"为什么不直接 import，为什么用 Protocol 而不是 ABC"。

**复盘写作原则**：
- 根因写"机制"不写"现象"——"看不到 import" 不是根因，"PowerShell 管道流式消费"才是
- 修复写"为什么有效"——"加个 sleep"不是答案，"让 close 显式调用避免 GC 延迟"才是
- 涉及技术点给出"最小阅读材料"链接，新人照着 1 小时能上手

**复盘不是目的，W3 之后会继续更新**。如果 W3 阶段又踩新坑，加 §3-§4 的小节继续累积。
