### 0.2 关键决策链

W1-W2 沉淀下来的两条工程守则主导了 W3-W6 的设计走向：

- **守则 A：抽象层加新方法前，先查"旧代码会怎么调它"** —— 让 W3 的 MySQLRepository 走 Protocol 而不是新接口；W4-W6 的所有改动都保证旧测试零修改通过。
- **守则 B：跨进程的接口要"幂等 + 显式 close"** —— W3 的 MySQL engine 走 `with` 上下文管理；W4 的工厂按 `mode` 路由容器；W6 的 AuthService 自己拥有 container 时 login 后 close，注入时不 close。

## 1. W3 阶段：MySQL Repository 实现

W3 的核心交付是 `src/ielts_buddy/repositories/mysql_repo.py`（1342 行，6 个 MySQL Repository + Container + 工厂 + 5 个默认连接参数）和 41 个 `test_mysql_repo.py` 单测。W3 阶段**没有遇到阻塞性问题**，但有 3 个值得记的设计决策和 1 个真实 bug。

### 1.1 真实 bug：`add_word` 类型签名收得太窄

**现象**：W3 单测 `test_mysql_repo.py` 跑 `PersonalVocabRepository.add_word(user_id, pw: PersonalWord)`，但 `vocab_service.add_to_personal()` 传的是 `Word` 实例（来自内置词库），立刻 `TypeError: argument 'pw': incompatible type`。

**排查**：看 `Word` 和 `PersonalWord` 的差异——`Word` 没有 `category_id` / `added_at`，但其它字段（word, meaning, phonetic, band, topic）都齐。SQL 列存的是 word/phonetic/meaning/band/topic/category_id/added_at/source 这些，跟两个模型都兼容。

**根因**：W2 写 `SQLitePersonalVocabRepository.add_word` 时只接 `PersonalWord`，是"下游传什么就接什么"的偷懒。W3 复刻签名时没重新考虑上游实际传的类型。

**解决**：

```python
def add_word(self, user_id: int, pw: "Word | PersonalWord") -> int:
    word = pw.word
    meaning = getattr(pw, "meaning", "") or ""
    phonetic = getattr(pw, "phonetic", "") or ""
    # ... 用 getattr 兜底两个模型都缺的字段
```

**决策逻辑**：与其让上游强制转换类型（侵入业务），不如 Repository 接受最宽类型并用 `getattr` 兜底。这是 Repository 的"宽进严出"原则——只关心 SQL 列值，不关心入参是哪个 Pydantic 模型。

**原理**：Pydantic v2 的 `model_dump()` 会按字段定义取值，对未定义字段静默丢弃；但 `getattr(obj, "x", default)` 在 duck typing 下能跨模型工作。两个 Pydantic 模型即使是不同类，只要字段名相同就能被 SQL 层等价处理。

### 1.2 决策：MySQL 与 SQLite 的 schema 差异显式抽出

**问题**：MySQL 用 `BIGINT AUTO_INCREMENT`、SQLite 用 `INTEGER AUTOINCREMENT`；MySQL 有引擎和字符集、SQLite 没有；MySQL 拿 `last_insert_id()`、SQLite 拿 `last_insert_rowid()`。

**方案**：W3 没有强行用 SQLAlchemy ORM 抹平差异，而是用 **Core 层（Table / Column / MetaData）** 让表结构两边各自手写，方法签名严格按 Protocol。

**决策逻辑**：

1. **ORM 会让两边的迁移逻辑不透明**（自动生成的 DDL 不可控），不符合"幂等 + 显式"原则。
2. **Core 层 + 同名方法**让 Service 层完全无感：调用 `container.personal_vocab.add_word(...)` 不需要知道背后是 SQLite 还是 MySQL。
3. **代价**：每个方法都要写两份（sqlite_repo.py / mysql_repo.py）。W3 接受了 1342 行的代码冗余，换取显式可控。

### 1.3 决策：seed 模板用 `user_id=0` 作为系统占位

**问题**：新用户首登时如何拥有"收藏 / 错词"两个系统分类？硬编码还是动态？

**方案**：

- `users` 表里有一条 `id=0, username="__system__"` 的种子行
- `personal_vocab_categories` 表里预先有 `favorites` / `mistakes` 两个 `user_id=0, is_system=1` 的分类
- 新用户首次 `add_word` 时，`_ensure_system_categories(user_id)` 用 `INSERT INTO ... SELECT ... WHERE NOT EXISTS` 把 user_id=0 的行复制一份

**决策逻辑**：
- 比"每次 add_word 前查表"高效（一次复制，后续 `is_system=1` 分类在用户维度查表）
- 比"硬编码 + 程序生成"灵活（分类文案/数量改了只需改 seed，不需改 Service 代码）
- 用 `WHERE NOT EXISTS` 保证幂等（同一用户多次调用不会重复插）

### 1.4 决策：MySQL 容器的"延迟导入"

`__init__.py` 里：

```python
try:
    from ielts_buddy.repositories.mysql_repo import (...)
    _MYSQL_AVAILABLE = True
except ImportError:
    _MYSQL_AVAILABLE = False
```

**决策逻辑**：

- 单机用户（80% 场景）不应被强制装 SQLAlchemy + PyMySQL（启动慢 1.5s，pip 多两个依赖）
- `local` 模式完全不碰 MySQL 模块；`online` 模式才需要它们
- `ImportError` 而非 `ImportWarning`，因为缺失时 offline 运行不应有任何提示

### 1.5 W3 涉及技术点

| 知识 | 用途 |
|---|---|
| SQLAlchemy 2.0 Core（Table/Column/insert/select/update） | MySQL Repository 实现 |
| PyMySQL 驱动 | 真实 MySQL 连接 |
| Pydantic 模型 duck typing | `Word \| PersonalWord` 兼容入参 |
| `INSERT ... SELECT ... WHERE NOT EXISTS` 模式 | 幂等的 seed 复制 |
| `cursor.lastrowid` / `result.inserted_primary_key` | 拿自增主键 |
| MySQL `BIGINT` vs SQLite `INTEGER` 方言 | DDL 抽取 |

## 2. W4 阶段：mode 分发 + Service 接入

W4 的核心交付是 `create_repositories(mode)` 工厂 + `get_mode()` / `get_mysql_url()` 解析器 + 7 个 Service 改造（其中 2 个仅改 mode 路由，5 个带了 user_id 注入的伏笔）。遇到 1 个值得说的设计权衡和 1 个真实的连锁问题。

### 2.1 决策：mode 解析走"env > config > 默认"

```python
def get_mode(config: Config | None = None) -> str:
    env_mode = os.environ.get("IELTS_BUDDY_MODE", "").strip().lower()
    if env_mode in VALID_MODES:
        return env_mode
    if config is not None:
        cfg_mode = str(config.get("general.mode", "local")).strip().lower()
        if cfg_mode in VALID_MODES:
            return cfg_mode
    return "local"
```

**决策逻辑**：

- **环境变量优先级最高**：CI / 临时切换不应改配置文件
- **配置文件次之**：是用户主动写下的偏好
- **默认 local**：单机模式兜底，新装环境零配置可跑
- **任何非法值都退回 local 并 warn**：不让拼写错误静默生效

### 2.2 决策：`Service(db_path=...)` 显式路径强制走 local

```python
class StatsService:
    def __init__(self, db_path: Path | None = None, user_id: int | None = None) -> None:
        if db_path is not None:
            self._container = create_repositories(mode="local", db_path=db_path)
        else:
            from ielts_buddy.core.config import Config, get_mode
            self._container = create_repositories(mode=get_mode(Config()))
```

**决策逻辑**：

- 旧测试大量传 `Service(db_path=tmp_path / "x.db")` 拿隔离数据库
- 强制 local 模式**保留旧测试零修改通过**（W2 守则 A 的延续）
- 未传 db_path 才走 config（生产场景）
- 这是"双轨"接口：测试场景 vs 生产场景不需要共享入口

**这是个隐性契约**：未来如果有人写"我传 db_path 但想走 online 模式"，会一脸懵。补救办法是在 docstring 里写明"W4 阶段：传 db_path 即强制 local 模式"。

### 2.3 真实问题：`recommend_service` / `report_service` 的 user_id 缺口

**现象**：W4 改造 7 个 Service 时，前 5 个都有 `_user_id = 1` 的硬编码；后 2 个（`recommend_service.py` / `report_service.py`）**没有** self._user_id 字段。

**排查**：看两个 service 的 SQL 查询，都是 `SELECT ... FROM learning_records` 不带 `WHERE user_id = ?`——本来就没做用户隔离。

**根因**：W2 阶段"加 user_id 字段"是按 Service 实际用到的范围来加的，`recommend` / `report` 没动 SQL，自然没暴露 `_user_id`。

**解决**：W4 阶段**只把它们改造为走 `create_repositories(mode=...)` 工厂**，不加 `_user_id`。等 W5 再统一处理。

**决策逻辑**：

- W4 范围是"mode 分发"，不要被 user_id 扩散
- W5 阶段会一次性注入 5 个 service 的 user_id，剩 2 个按"是否需要 user_id 隔离"再决定
- 守则 A：每一阶段只动当前阶段承诺的范围，避免"顺手改"

### 2.4 W4 的连锁问题：5 个 Service 的 user_id 漏改如何补救

**问题**：W4 漏了 2 个 Service 的 user_id；W5 阶段如果忘了"漏改"会回归。

**方案**：W5 第一步**主动 audit** 7 个 Service 的 SQL 查询，列出"哪些 service 的 SQL 涉及 user_id，哪些不涉及"。然后按"涉及 + 未注入"的清单改造。

**决策逻辑**：

- audit 比"凭印象"少遗漏
- W5 的 test_user_id_resolution.py 用 `@pytest.mark.parametrize` 把 5 个 service 跑同一个测试模板，**任何一个漏改都会被同一个测试抓到**

### 2.5 W4 涉及技术点

| 知识 | 用途 |
|---|---|
| `os.environ.get()` + `config.get()` 双源解析 | `get_mode` / `get_mysql_url` / `get_user_id` |
| `try / except ImportError` 延迟导入 | MySQL 可选依赖 |
| 双轨构造函数（`db_path=None` 走 config） | 兼容旧测试 + 满足生产 |
| pytest parametrize 表驱动 | 统一测 5/6 个 Service |

## 3. W5 阶段：user_id 注入

W5 的核心交付是 `get_user_id()` 解析器（与 `get_mode` 同源设计）+ 5 个 Service 注入 user_id + 35 个 `test_user_id_resolution.py` 单测。踩了 1 个**测试隔离**的坑。

### 3.1 决策：user_id 解析与 mode 解析同源

```python
def get_user_id(config: Config | None = None) -> int:
    env = os.environ.get("IELTS_BUDDY_USER_ID", "").strip()
    if env:
        try:
            v = int(env); ...
        except ValueError:
            warnings.warn(...)
    if config is not None:
        cfg_val = config.get("database.user_id", None)
        if cfg_val is not None:
            ...
    return 1
```

**决策逻辑**：

- 与 `get_mode()` 同样的"env > config > 默认"三层结构，团队不需要记两套规则
- 默认 1 而不是 0，因为单机模式 `SQLiteUserRepository.get_or_create("any")` 固定返回 1
- **联网模式登录后**真实 user_id 由 W6 的 `AuthService.login()` 写回 config（这是 W5 → W6 的接口约定）

### 3.2 真实问题：`test_review_user_id_isolated` 两个 service 共享 db_path

**现象**：测试断言"两个 user 的 review 记录互不可见"——user_a 复习了 5 个词，user_b 应该看到 0 个。**但断言失败**，user_b 看到了 user_a 的 5 个。

**排查**：两个 `ReviewService` 实例化时传同一个 `tmp_path / "data.db"`，按理 SQLite 的 `IF NOT EXISTS` 不会让 user_a 的 INSERT 影响 user_b 的 SELECT——但实测是影响的。

**根因**：两个 Service 共享同一个 SQLite 连接（因为 container 走的是 `db_path` 而不是 `db_path + user_id` 派生文件），**`learning_records` 表的 `user_id` 列就是隔离边界**。看 SQL 是对的：

```sql
SELECT COUNT(*) FROM learning_records WHERE user_id = ? AND ...
```

但测试 fixture 没清理——**第一个 service 写的行还在，第二个 service 拿到的 COUNT 是 6（自己的 1 + 对方的 5）**。

**解决**：

```python
@pytest.fixture
def user_a_service(tmp_path):
    return ReviewService(db_path=tmp_path / "a.db", user_id=1)  # 物理隔离

@pytest.fixture
def user_b_service(tmp_path):
    return ReviewService(db_path=tmp_path / "b.db", user_id=2)
```

**决策逻辑**：

- 业务上 user_id 已经是隔离边界（SQL 写了 WHERE user_id = ?），测试再用同 db_path 验证隔离意义不大
- 用两个独立文件**测试两层语义**："user_id 列确实在隔离" + "db_path 物理隔离"——后者是退路
- 这是"测试金字塔"的权衡：单测测接口契约，集成测测物理边界

**原理**：`ReviewService` 不会主动清表；如果新 fixture 创建一个空 db，第二个 fixture 不会清第一个。**默认 SQLite db 不会自清理**——这跟 in-memory SQLite（`:memory:`）行为不同。

### 3.3 决策：user_id=0 也允许（系统模板场景）

```python
if v >= 0: return v
```

**决策逻辑**：

- W3 设计的 seed 模板用 `user_id=0` 作为系统占位
- 显式注入 `user_id=0` 给"系统级清理 / 迁移脚本"用，是合法场景
- 不允许负数（语义无意义）

### 3.4 W5 涉及技术点

| 知识 | 用途 |
|---|---|
| env > config > 默认 三层解析 | 与 get_mode 同源 |
| 物理隔离 vs 逻辑隔离（user_id 列） | 测试 fixture 设计 |
| parametrize 把 5 个 service 跑同一模板 | 漏改的兜底 |
| `monkeypatch.setenv / delenv` | 测试隔离环境变量 |

## 4. W6 阶段：AuthService + ib auth CLI

W6 的核心交付是 `services/auth_service.py`（235 行）+ `commands/auth.py`（70 行）+ cli.py 注册 + 50 个新测试。遇到 4 个**值得记的真实问题**和 3 个**设计权衡**。

### 4.1 真实问题 1：`PowerShell` shim 把 `python` 当成 GUI 目标

**现象**：`python 'C:\...\smoke.py'` 报 `Shim: Could not determine if target is a GUI app. Assuming console.` 然后 `Shim: Could not create process`，exit 1。

**排查**：shim 是 TRAE 在用户级别注册的 `python.exe` 包装器；它对**带引号参数**的处理有 bug——会把整个引号包裹的命令行当 GUI 目标。

**根因**：shim 的参数解析在嵌套引号时（外层 `"..."` 套内层 `...`）退化成 GUI 模式判断。

**解决**：

1. 改用 `py`（Python launcher）而不是 `python`（shim 路径）
2. 把 `python -c '...'` 改成临时 `.py` 脚本再 `py script.py`

**原理**：Windows 的 Python launcher（`py.exe`）由 `python.org` 官方提供，**不经过任何 shim**，是稳定的"找解释器"路径。社区共识是 CI/脚本里优先用 `py` 而不是 `python`。

**涉及技术点**：
- `py` vs `python` vs `python3` 在 Windows 的差异
- 第三方 shim 的兼容性陷阱
- 临时脚本规避引号嵌套

### 4.2 真实问题 2：`tests/conftest.py` autouse fixture 默认关闭 banner

W6 在 cli.py 加了启动 banner（"当前用户: alice"），但**老 CLI 测试**断言 `result.output` 包含某些子命令输出，banner 出现在 output 头部导致 7 个测试 fail。

**第一版方案**（失败）：`_show_current_user` 检查 `os.environ.get("PYTEST_CURRENT_TEST")`，pytest 9 跑测试时会设置这个变量——**但仅在 test function 调用期间设置**，autouse fixture 跑完时它被设回。

**debug 过程**：
```python
[debug] _enable_banner: PYTEST_CURRENT_TEST=None   # autouse 跑完
[debug] before invoke: PYTEST_CURRENT_TEST='::TestCurrentUserBanner::test_banner_when_not_logged_in (call)'  # pytest 又设了
```

**第二版方案**（成功）：把 banner 默认关闭，开关用显式环境变量：

```python
# cli.py
if os.environ.get("IELTS_BUDDY_NO_BANNER", "").strip() in ("1", "true", "yes"):
    return

# conftest.py
@pytest.fixture(autouse=True)
def _disable_cli_banner(monkeypatch):
    monkeypatch.setenv("IELTS_BUDDY_NO_BANNER", "1")
    yield
```

W6 的 banner 测试在 `TestCurrentUserBanner` 里用 `monkeypatch.delenv("IELTS_BUDDY_NO_BANNER", raising=False)` 单独打开。

**根因**：pytest 9 在 test 范围内自动重设 `PYTEST_CURRENT_TEST`，**monkeypatch 的 delenv 在 test 进入前会被覆盖**——这是 pytest 的内部约定，不是 bug。

**决策逻辑**：

- 不要依赖 pytest 的内部变量做开关（不稳定）
- 用项目自己的环境变量 + autouse 默认设值（稳定 + 显式）
- 需要打开的测试在自己 fixture 里 delenv 即可

**原理**：pytest 的 autouse fixture 是"setup 时执行"的，monkeypatch 作用域默认是 function（test 级别），但**变量重设发生在 fixture 之间**——autouse fixture 跑完后到 test body 之前，pytest 还会做一轮"re-enable internal state"，`PYTEST_CURRENT_TEST` 就是这样被重新设置的。

### 4.3 真实问题 3：`test_cli.py` 期望字符串过时

**现象**：`test_help` 断言 `'IELTS Buddy' in result.output`，但 cli.py 的 description 是 `'IELTS LEARNING SEEK - 雅思学习-不断求索'`。

**根因**：项目早期可能叫 "IELTS Buddy"，后来改名为 "IELTS LEARNING SEEK"，老测试没跟上。

**解决**：按用户建议，把 `assert "IELTS Buddy" in result.output` 改成 `assert "IELTS LEARNING SEEK" in result.output`——纯字符串匹配，业务代码不动。

**决策逻辑**：用户原话"如果只是测试用到，可以修改"——指的就是这种**纯字符串断言**，不动业务代码。

### 4.4 真实问题 4：`test_grade_deploy_cli.py` 6 个 grade 测试输入太短

**现象**：`test_grade_shows_scores` 用 `input="Test essay text.\n"`（16 字符），但 grade 命令预校验"至少 50 字符"，mock subprocess.run 没被调用，断言失败。

**根因**：grade 命令在某次（推测 W3 之前）加了输入长度预校验，老测试没同步更新。

**决策**：W6 阶段**不修这些测试**——属于 W7 范围（"未登录时其他业务命令的优雅降级"），需要在 W7 决定"grade 命令是否要降级"之后再批量改测试。

**决策逻辑**：

- W6 范围是"auth 系统"，不顺手改 grade 测试
- 6 个 fail 跟 W6 改动**零关联**（即使把 W6 改动全部 revert，这些测试仍然 fail）
- W7 重新打开这些测试，**结合 W7 的"未登录降级"决策**统一改

### 4.5 决策：session.json 写到 `~/.ielts-buddy/session.json`

**理由**：

- 与 `plan.json` / `email.json` / `feishu.json` 同目录
- 复用 `get_app_dir()`，单点决定"用户数据位置"
- 环境变量 `IELTS_BUDDY_HOME` 可重定向（测试用 monkeypatch.setenv）

**反例**：写到 `~/.config/ielts-buddy/session.json`（XDG 规范）—— 跨平台但**单点改动要改 4 处**。

### 4.6 决策：banner 写到 stderr 而非 stdout

```python
console = Console(stderr=True)
console.print("[dim]-- 当前用户: alice --[/dim]")
```

**理由**：

- 用户 `ib stats show > out.txt` 重定向 stdout 到文件时，banner 不进文件（不影响业务输出）
- banner 是"提示信息"语义，应该与 stdout 的"业务输出"分离
- 测试用 `CliRunner` 默认 mix_stderr=True（Click 8.2 之前），老测试会受影响——所以引入 `IELTS_BUDDY_NO_BANNER` 开关

### 4.7 决策：AuthService 支持 `container` 注入

```python
def __init__(self, mode=None, session_path=None, container=None, config=None):
    self._owns_container = container is None
```

**理由**：

- 单元测试可以注入 FakeContainer 避免连真实 MySQL/SQLite
- 业务代码用 `AuthService()` 让 service 自己拥有 container，login 后 `close()` 释放
- `_owns_container` 标志位让 `close()` 只关闭自己创建的，不影响外部注入

**对比**：如果 AuthService 总是自己建容器，单元测试就要 mock `create_repositories`——侵入性更大。

### 4.8 W6 涉及技术点

| 知识 | 用途 |
|---|---|
| `py` launcher（不经过 shim） | 跨 Windows 环境的稳定 Python 调用 |
| `Console(stderr=True)` | banner 与 stdout 业务输出分离 |
| 显式环境变量 + autouse fixture | 跨测试隔离的开关 |
| monkeypatch.delenv + autouse setenv | test 级别环境控制 |
| CliRunner 的 stderr 行为（Click 8.2 前后差异） | CLI 测试设计 |
| `@click.confirmation_option` | logout 二次确认 |
| 工厂方法 `create_repositories(mode)` | W4-W6 一致的容器入口 |

## 5. 跨阶段经验提炼

W1-W2 的 4 条守则 + W3-W6 的 4 条新守则，构成项目的工程约束。

### 5.1 守则 1：抽象层加新方法前，先查"旧代码会怎么调它"（W1-W2 沉淀，W3-W6 验证）

- W3 的 MySQLRepository 走 Protocol 而不是新接口 → 7 个 Service 零修改
- W4 的 `create_repositories(mode)` 让 Service 只换工厂调用 → 旧测试不改
- W6 的 `AuthService(container=...)` 让 Service 与测试都拿到同一接口

### 5.2 守则 2：跨进程/跨工具的接口，要用幂等 + 显式 close（W1-W2 沉淀，W3-W6 验证）

- W3 的 MySQL `engine.begin()` 走 context manager
- W4 的 `create_repositories(mode)` 工厂返回的容器都有 `close()`
- W6 的 AuthService 区分"自有 container"和"注入 container"两种 close 语义

### 5.3 守则 3：避免模块循环依赖的最稳办法是"接口不调实现"（W1-W2 沉淀）

W3-W6 期间没新增循环，但 W6 的 `AuthService` 接受了**不持有 container** 的设计——只调 `user_repo.get_or_create / update_last_login / ensure_system_categories` 这 3 个 Protocol 方法，不依赖具体类。W3 的 `ensure_system_categories` 内部又调 `MySQLPersonalVocabRepository._ensure_system_categories`（同包内调用，不算跨模块）——这条边界守住了。

### 5.4 守则 4：测试 Protocol 风格的接口时，运行时的 `inspect.signature` / `__annotations__` 与 `dir()` 行为不同（W1-W2 沉淀）

W3-W6 期间这条没新增踩坑，但 W4 的 test_mode_factory 测的是 `create_repositories` 工厂返回的对象——`assert "learning" in container.__dict__`（具体类有 `__dict__`），不依赖 `dir()`，验证了 W1 的认知。

### 5.5 守则 5（新增）：每一阶段只动当前阶段承诺的范围

- W4 没顺手改 `recommend_service` / `report_service` 的 user_id（留给 W5）
- W6 没顺手改 `test_grade_deploy_cli.py` 的 6 个输入太短的 grade 测试（留给 W7）
- 守则来自"避免范围爆炸"——每个阶段保持 5-7 个小任务、300-500 行代码、几十个测试

### 5.6 守则 6（新增）：环境变量是跨阶段的"显式契约"

- `IELTS_BUDDY_MODE` / `MYSQL_URL` / `IELTS_BUDDY_USER_ID` / `IELTS_BUDDY_NO_BANNER` 都是"项目自定义但团队共识"
- 比"配置文件 + 代码"更显式（`os.environ.get` 一眼可见）
- 比"全局变量"更隔离（每个进程独立）
- 测试用 `monkeypatch.setenv / delenv` 完整可控

### 5.7 守则 7（新增）：banner / 提示信息写到 stderr，stdout 只放业务输出

- 让 `>` 重定向不影响 banner
- 让 `|` 管道只接业务结果
- 测试用 `IELTS_BUDDY_NO_BANNER=1` 显式关闭（不要靠 `PYTEST_CURRENT_TEST` 这种 pytest 内部变量）

### 5.8 守则 8（新增）：pytest autouse fixture 是稳定的"全局开关"位

- 写 `tests/conftest.py` 的 autouse fixture 比"每个测试自己 monkeypatch"更可靠
- 关闭 banner、设置隔离 HOME、清环境变量都适合放 autouse
- 需要"开"的测试在自己 class fixture 里 `monkeypatch.delenv` 即可

## 7. 给 W7+ 工作的预警

### 7.1 W7 范围决策已定：未登录不阻断

W7 决定"未登录时业务命令不阻断，user_id=1 默认通过"。这意味着：

- 所有 Service 的 `__init__` 已经支持 `user_id=None`（W5 已完成）—— 未传就是默认
- 但部分 Service **没有读 self._user_id**（recommend / report）—— W7 第一步要先 audit
- CLI 层不阻断：`ib vocab add` 在未登录时仍可调用，写入 `user_id=1`（单机默认）
- 文案层加 1 句提示：未登录时 `stats show` 等命令的输出顶部加"提示：未登录，数据保存到本地 user_id=1"

### 7.2 W7 可能踩到的坑

**坑 1：6 个 grade 测试输入太短（pre-existing）**

W6 末尾已识别 6 个 fail：`test_grade_deploy_cli.py::TestGradeCLI::test_grade_*` 的 input 字符串 11/16/33 字符，触发了"作文太短"预校验。W7 修法是把 input 改长到 ≥ 50 字符。

**坑 2：MySQL 模式 user_id 默认值**

单机模式默认 user_id=1 是合理的；MySQL 模式下 `get_user_id()` 默认 1 在未登录时会让所有用户**共享同一份数据**——这是严重的语义错误。

W7 修法：MySQL 模式 + 未登录 → 阻断（要求登录），或者自动创建一个匿名账户。

**坑 3：session 文件损坏时的兜底**

`AuthService.whoami()` 已经处理"JSON 损坏返回 None"，但 session.json 字段缺失（如只写了 user_id 没写 username）时，`require_login()` 会返回带缺字段的 dict，调用方可能崩。

W7 修法：在 `_read_session` 里加字段完整性校验，缺关键字段视为未登录。

**坑 4：多个 CLI 进程并发写 session.json**

`login` 和 `logout` 并发时可能丢更新（last write wins）。W7 之前是单机单进程场景，不需要锁；引入多终端时需要 `fcntl.flock` / `msvcrt.locking`。

**坑 5：banner 在 Windows Terminal / WSL 下的渲染**

`Console(stderr=True)` 在 Windows Terminal 正常，在 WSL 下需要 `WT_SESSION` 环境变量。W7 验证跨终端兼容性。

### 7.3 跨 W7-W8 的工程关注点

- **离线 vs 在线模式的统一语义**：`ib auth login` 在 local 模式下仍然是"假登录"（user_id 始终 1）。需要在 `whoami` 输出里区分"本地默认用户"和"联网真实用户"。
- **session 与 config 的双重真相源**：`session.json` 和 `config.toml` 都有 user_id，登录后两边都写。但 logout 只删 session，不清 config（设计上没问题：下次 login 会覆盖）。W8 也许要做"清理工具"。
- **MySQL 模式的种子数据同步**：单机模式的 seed 在 SQLite 文件里，MySQL 模式的 seed 在 `user_id=0` 的远端行里。W8 写"切换模式数据迁移"时要考虑两边 seed 的对应关系。

## 9. 复盘方法说明（沿用 W1_W2 的原则）

> **为什么持续做复盘**：项目没有 PM，开发者要自我管理"为什么这样改"的解释链。每阶段 50+ 个测试、300-500 行代码、3-5 个新文件，6 个月后没人记得"为什么 add_word 接受 Word | PersonalWord"。

**复盘写作原则（与 W1_W2 一致）**：

- 根因写"机制"不写"现象"——"pytest 9 重设 PYTEST_CURRENT_TEST" 是机制，"banner 不显示" 是现象
- 修复写"为什么有效"——"autouse fixture 默认设 IELTS_BUDDY_NO_BANNER=1" 是答案，"加个开关" 不是
- 决策写"备选 + 理由"——ORM vs Core、stderr vs stdout、env vs config，每条决策都有"备选方案 + 为什么没选"
- 涉及技术点给最小阅读材料（如有链接）

**复盘与代码同步**：

- W1-W2 复盘：`docs/W1_W2_阶段问题复盘.md`
- W3 设计详解：`docs/W3_阶段详解与扩展指南.md`
