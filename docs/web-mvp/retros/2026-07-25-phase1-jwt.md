# 2026-07-25 阶段 1 复盘

## 1. FastAPI 路由里 `response.set_cookie` 不下发 → 必须复用形参 response

### 现象
阶段 1 写完第一版后，`test_refresh_invalid_token_clears_cookie` 和
`test_logout_clears_cookie` 失败。失败信息：
```
AssertionError: assert 'ib_refresh' in ''
```

### 定位
打印 `response.headers.get_list("set-cookie")` 是空列表。
代码原本是：
```python
@api_router.post("/logout")
def api_logout(response: Response) -> Response:
    _clear_refresh_cookie(response)   # 写到了"形参 response"上
    return Response(status_code=204)  # 实际返回的是新建的空 response
```

而 `api_refresh` 走的是：
```python
return _auth_error_response(e)  # 新建 JSONResponse
```

`Response.set_cookie` / `delete_cookie` 实际是写到 `self.raw_headers` 的，
只有真正作为最终返回值的那个 Response 对象，starlette 才会序列化下发。
新建的 `Response` / `JSONResponse` 虽然带了 `Set-Cookie` 头，但从来没被返回。

### 根因
- 没有意识到 FastAPI 的 "形参 `response: Response`" 注入的是"空壳 response"，
  starlette 会把它作为最终响应写出。
- 习惯于返回 Pydantic 模型 / `JSONResponse`，完全忘了形参的副作用。

### 解决方案
所有"要带 cookie 副作用"的端点，必须复用 `response` 形参：

```python
@api_router.post("/logout", status_code=204)
def api_logout(response: Response) -> Response:
    _clear_refresh_cookie(response)
    response.status_code = 204
    return response     # ← 必须返回这个形参
```

refresh 端点类似处理：成功失败两条分支都把 body / status_code 写到 `response` 上再 return。

### 决策思路
- 不引入额外 wrapper 函数（容易再次踩坑）
- 不让 service 知道 cookie（关注点分离）

### 技术沉淀
- FastAPI / starlette 的"形参 response"是约定俗成的副作用通道，文档在
  [Starlette Responses](https://www.starlette.io/responses/) "Setting Cookies"
  一节有写，但很容易被忘记。
- 后续**所有要下发 cookie / 自定义 header 的路由都强制复用 response 形参**，
  不要用 `return JSONResponse(...)` 偷懒。

## 2. `passlib` 1.7.4 与 `bcrypt` 4.x+ 不兼容 → 弃用 passlib

### 现象
最初方案写的是 `passlib.context.CryptContext(schemes=["bcrypt"])`，跑测试
`hash_password` 报：
```
AttributeError: module 'bcrypt' has no attribute '__about__'
```
或
```
ValueError: password cannot be longer than 72 bytes
```
（实际 passlib 内部调用了 bcrypt 的私有属性）

### 定位
passlib 1.7.4（最后版本）发布于 2020 年，与 bcrypt 4.x 引入的
`__about__` 移除不兼容。这是社区已知问题，passlib 已停更。

### 解决方案
移除 passlib，直接用 bcrypt 库：
```python
import bcrypt
bcrypt.hashpw(password.encode()[:72], bcrypt.gensalt())
bcrypt.checkpw(password.encode()[:72], stored_hash.encode())
```

72 字节限制在业务层手动截断（`[:72]`），与历史实现保持一致。
`hash_password` / `verify_password` 都加了空值/异常保护，对错误 hash
返回 False 而不是抛异常（业务层只关心"通过/不通过"）。

### 决策思路
- 一个能用、好理解的库 > 一个不维护、文档漂亮的库
- 业务层不暴露 bcrypt 4.x 的告警细节，全在 security 模块消化

### 技术沉淀
- 选第三方库要看维护状态 + Python 主版本适配
- 阶段 1 锁 `bcrypt>=4.0` 即可；锁到 4.1 防止 5.x 又有 breaking change

## 3. FastAPI 同步端点 + sqlite3 跨线程 → `check_same_thread=False`

### 现象
登录接口跑测试偶发：
```
sqlite3.ProgrammingError: SQLite objects created in a thread can only
be used in that same thread
```

### 定位
FastAPI 同步端点（`def` 而非 `async def`）默认在线程池跑，每个请求可能落到
不同 worker。sqlite3 默认 `check_same_thread=True`，跨线程访问连接直接抛。

### 解决方案
`create_sqlite_web_user_repository` 构造连接时关掉：
```python
conn = sqlite3.connect(db_path, check_same_thread=False)
```
并在 app `lifespan` 中由 `create_app()` 统一打开 / 关闭。
MySQL 实现通过 SQLAlchemy 连接池，天然线程安全。

### 决策思路
- Web 端始终是"多 worker / 多线程"模式，SQLite 必须是线程安全连接
- `check_same_thread=False` + 自己控制连接生命周期，比换 aiosqlite 简单

### 技术沉淀
- FastAPI 同步端点 ≠ 单线程；写 SQLite / 文件类资源要明确线程模型
- 阶段 1 文档明确"SQLite 仅供 dev / 测试用，生产必须切 MySQL"

## 4. JWT dev 默认密钥导致重启 token 全失效

### 现象
`config.py` 检测到 `IELTS_BUDDY_JWT_SECRET` 缺失时，随机生成临时密钥。
测试看着 OK，但**生产部署忘设环境变量**会出大问题：
所有已签发 token 在重启后全部失效，所有用户被强制重新登录。

### 决策
```python
if os.environ.get("IELTS_BUDDY_ENV", "dev") == "prod":
    raise RuntimeError("生产环境必须设置 IELTS_BUDDY_JWT_SECRET（≥32 字符）")
fallback = secrets.token_urlsafe(48)
warnings.warn("...重启后所有 token 失效...")
return fallback
```

dev 友好（开箱即用），prod 强约束（直接启动失败，运维必看错误信息）。
启动后用 `os.environ.setdefault` 在 lifespan 里也置一次，lifespan 关闭时不需要清。

### 技术沉淀
- 任何"安全相关默认"都要区分 dev / prod
- `os.environ.setdefault` 让"显式覆盖"和"自动生成"和平共存

## 5. WebUser 表与 CLI users 表的字段差异

### 差异
- CLI `users`：`username + mode` （无密码）
- Web `web_users`：`email + password_hash + created_at + last_login_at`

### 决策
不复用 `users` 表、不复用 `core/repository.py` 里的 `UserRepository`。
Web 端独立建 `WebUserRepository`（同 Protocol 风格），新 MySQL 表 `web_users`。

### 技术沉淀
- 不要为了"省表"去复用结构语义不同的表
- 用户体系是业务核心，独立设计更利于未来多渠道扩展
