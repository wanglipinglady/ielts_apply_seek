# 2026-07-25 阶段 1：Web 端 JWT 认证落地

## 目标
为 Web 端建立独立的用户体系与 JWT 认证：邮箱 + 密码注册登录，access_token 走
`Authorization: Bearer ...`，refresh_token 走 `HttpOnly` Cookie。多用户隔离
（`web_users` 与 CLI 的 `users` 物理隔离）。

## 关键设计决策

1. **不复用 CLI 的 `UserRepository`** — CLI 表 `users` 是 username 模式、无 password_hash，
   改它会污染 CLI 路径。Web 单独建 `WebUserRepository`（同 Protocol 风格），与
   `users` 物理隔离。
2. **JWT access / refresh 通过 `aud` 区分** — `aud=ielts-buddy:access` vs
   `aud=ielts-buddy:refresh`，避免拿 access 当 refresh 用、拿 refresh 当 access 用。
3. **密码哈希直接用 `bcrypt` 库，不走 `passlib`** — passlib 1.7.4 停更且与 bcrypt
   4.x 不兼容；直接用 `bcrypt.hashpw` / `bcrypt.checkpw`，逻辑更可控。
4. **refresh token 走 `HttpOnly` Cookie，`path=/api/auth`** — 最小化暴露面：浏览器
   只在 auth 路由携带，业务路由完全不接触。
5. **service 抛 `AuthError(code, message)`，路由统一翻译** — service 不依赖 FastAPI，
   纯 Python 业务逻辑，方便单测。
6. **`check_same_thread=False`** — FastAPI 同步端点在 threadpool 跑，sqlite3 默认
   跨线程报错；关掉后读写正常，连接由 app 生命周期管理。
7. **路由层显式复用 `response` 形参** — 见复盘 §1。
8. **注册即自动登录** — 成功同时返回 token 集合，前端不用再发一次 login 请求。
9. **邮箱大小写不敏感** — `COLLATE NOCASE` + service 内统一 `strip().lower()`。
10. **失败信息不区分** — 邮箱不存在 / 密码错误都返回 `INVALID_CREDENTIALS`，
    避免邮箱枚举。

## 剩余需人工验证（已写清单）

详见 `docs/web-mvp/manual-verify-phase-1.md`：
- 浏览器打开 `/register` 实际注册
- 浏览器登录后能否看到 Dashboard 显示当前邮箱
- 登出后再访问 `/dashboard` 应跳 `/login`
- DevTools 看 `ib_refresh` cookie 的 `HttpOnly` / `Path` 属性
- `JWT_SECRET` 缺失时的 fallback 行为（仅 dev 警告）

## 风险点

- **生产环境务必显式设 `IELTS_BUDDY_JWT_SECRET`** — 否则每次重启 token 全失效；
  阶段 1 在 dev 默认随机生成临时密钥并 warn。
- **MySQL 仓储未实现** — `WEB_DB_MODE=online` 会 raise，明确提示阶段 4 才补。
- **token 黑名单未实现** — 登出只清 cookie，access 需等 TTL 到期（默认 1h）。
